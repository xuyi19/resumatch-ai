**踩坑**：`FreeStartRequest.llm_config` 声明为严格 `dict` 时，前端未配置 Key 显式传 `null` 会被 Pydantic 422 拒掉——表现为「点击开始面试毫无反应」（请求在进 handler 前被拒，无会话行、toast 一闪而过）；curl/fetch 手测时省略了该字段走了默认值，导致多次复现失败。修复为 `dict | None` 并加回归用例。教训：**接口模型的可选字段必须容忍前端显式 null；前端「发了请求但后端无痕」优先怀疑 422**。

**Hotfix：面试 Tab「卡死」（同日）**
- **根因**：`run.py` 看门狗用 `browser_proc.wait()` 单信号判断——专属浏览器进程一退出（用户关掉弹窗改用自己浏览器、或 Chrome 把 URL 转发给已有实例后立即退出）就立刻杀掉前后端。结果页三个 Tab 里诊断/优化是 `v-show`（已渲染内容不受影响），唯独面试 Tab 是 `v-if` 挂载 + onMount 发 GET，服务死亡后该 Tab 表现为「点了没反应」，且错误被静默吞掉——用户感知为「面试 Tab 卡死」
- **修复**：
  - 后端新增 `POST/GET /meta/heartbeat`：前端 App 挂载即上报并每 20s 续报心跳；`run.py` 在浏览器进程退出后轮询心跳，仍有页面在用则继续服务，心跳消失（90s 阈值，覆盖后台标签页 1 次/分钟节流）才关停——「关浏览器自动退出」约束保留，误杀消除
  - `InterviewPanel.vue`：onMount 的会话恢复 GET 加载中/失败状态显式化（失败出横幅 + 重试按钮），不再静默吞错
- 教训：**「某单点功能卡死」而其余页面正常时，先怀疑该功能独有的一次性挂载请求 + 全局进程/服务异常**；看门狗类单信号防护必须区分「信号源退出」与「使用者退出」

**补优化（同日）**
- `POST /interview/mock/{task_id}` 的点评/总评此前硬编码 `llm_config=None`（走服务端默认 Key）——与出题端点不一致，无服务端 Key 时「能出题但答题必失败」。`MockReply` 增加 `llm_config: dict | None`，前端 `interviewMockReply` 与 `sendMockAnswer` 透传 `_llmCfg()`，补透传回归用例
- `call_llm_for_json` 增加 `total_timeout`（默认 150s）总时限：防「模型响应慢/JSON 反复不合法」时重试叠加拖到数分钟（axios 180s 先超时、后端继续空烧）；到点提前抛错，用户可拿到明确报错而非无限等待

## M29 诊断卡死修复 + 国内岗位数据源方案（2026-09-23）

**问题 1（诊断卡死）**：一直提示「已有诊断任务进行中」无法发起新诊断。根因：M16 跨重启恢复会把 waiting_clarify 任务重建进内存任务表，而 waiting_clarify 计入「进行中」状态，追问界面又没有放弃入口——不想回答旧追问的用户被永久 409。

- 新增 `POST /live/abandon/{task_id}`：内存 + DB 双清，立即释放名额；`abandoned` 标记阻断 run() 的 `_update`/终态落库（防在途复活），pending 瞬间放弃也安全
- 追问界面新增「不想继续了？放弃此任务」（确认弹窗 → 放弃 → 回分析页）
- 409 响应带 `X-Active-Task` 头，AnalyzeView 捕获后弹「前往该任务」引导，不再只有一句死提示
- 发起诊断前自动作废超过 24h 未应答的 waiting_clarify（内存+DB）

**问题 2（一键获取岗位）**：JSearch/Adzuna 均为海外岗位聚合器，不覆盖国内在招岗位——配好 Key 也搜不到国内岗位，属方案级缺陷。

**方案**
- 新增 `AIJobProvider`（provider=ai）：用用户已配置的 LLM 按关键词+城市生成典型岗位「参考画像」（国内公司风格、人民币薪资、完整 JD），明确标注「AI 参考岗位 · 非实时在招数据」；LLM 失败降级内置示例数据

- 验证：pytest 56 通过（新增 test_jobs_ai.py 4 例）；npm build 通过；实测放弃旧任务释放名额成功、AI 源真实模型返回 10 条国内岗位（阿里/网易/蚂蚁等风格画像）

**教训**

## Hotfix ResultView 白屏：TDZ 变量先用后声明（2026-09-23）

## M17 Web 形态压力摸底（2026-09-22）

**修改内容**
- 新增 `backend/scripts/stress_web.py` 压测脚本：进程内 uvicorn（port=0 随机端口）+ mock LLM 每节点延时 8s 拉长任务窗口；① 单诊断任务上阶梯开 25/50/100/150 条 SSE 连接（每波保持 7s），测首包延迟与进程内存 ② 20/60/120 工作循环并发插入 diagnosis_records（模拟进度节流写的极端化），测吞吐与锁错误；数据全部落 `tests/.tmp/stress/`
- 结论写入技术说明文档 13.4：SSE 150 并发全连上（首包 p50 0.35s / p95 0.47s / 0 错误 / 218MB，约 +0.6MB/连接）；WAL 写吞吐 ~350-400 ops/s（瓶颈在连接池 5+10 排队），busy_timeout=5000 下偶发 locked 约 0.03%

**遇到的问题与解决**
| 问题 | 解决 |
| --- | --- |
| `logging.getLogger("sqlalchemy.engine").setLevel(WARNING)` 放在 app 导入前不生效 | engine `echo=True` 在创建时强制重设 INFO——日志抑制必须放在 `app.core.db` 导入**之后** |
| ctypes `GetProcessMemoryInfo` 恒失败（内存读 -1） | 64 位下 `GetCurrentProcess()` 伪句柄被 ctypes 按 32 位 int 截断，需 `restype = ctypes.c_void_p` 后再传入 |
| SSE 推送只在 payload 变化时发包，无逐秒心跳 | 改测「首包延迟 + 事件数」而非心跳间隔，忠实反映 fan-out 响应能力 |
| 客户端与服务端同进程，GIL 竞争使延迟偏大 | 作为下界参考如实注明测法局限（真实部署为独立进程，结果只会更好） |

**验证**：脚本两次运行结果一致可复现；未触碰运行时 data/ 目录。
