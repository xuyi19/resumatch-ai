## 二、后端工程知识点

### 2.1 分层架构
```
api/v1/（路由+入参校验） → services/（业务编排） → agents/（LLM 工作流） → core/（配置/DB/检索） → models/
```
依赖注入贯穿：`get_db`（请求级会话）、`get_owner_id`（会话身份）——`core/deps.py`。

### 2.2 应用生命周期（lifespan，`main.py`）
- 启动：建表 → `ensure_schema_columns()` 老库自动补列（无感迁移）→ **启动补偿**把残留 running 任务标记失败（防重启僵尸）
- 优雅关闭：Uvicorn lifespan 信号

### 2.3 SSE 实时推送（`api/v1/live.py` stream_task）
- `StreamingResponse` + `text/event-stream`，诊断进度逐节点推送
- 断线恢复：SSE 断开 10 分钟内重连可续（内存任务表 TTL 1h）；过期回退 DB 快照（`get_task_from_db`，含 owner 校验）

### 2.4 数据隔离（多形态单表方案）
- 所有业务表带 `owner_id`；桌面形态固定 `local`；网站形态 HttpOnly 匿名 cookie（`rmsid`，30 天）或 `X-Session-Id` 头
- 不做用户系统即达多用户隔离 —— 答辩亮点：**轻量会话设计**

### 2.5 入参防线（`api/v1/live.py`）
- JD 最短 20 字；追问回答去空、≤10 条、单条截断 500 字（防超长回答撑爆 prompt）
- **重复诊断防护**（M13）：`LivePipelineService.has_active_task(owner)` —— 同 owner 存在 pending/running/waiting_clarify 任务时 409 拒绝，防双击重复发起浪费 LLM 调用

### 2.6 性能史（论文「性能优化」小节素材）
| 问题 | 修复 | 效果 |
|---|---|---|
| 桌面启动端口探测串行健康检查 | 先 `SO_EXCLUSIVEADDRUSE` bind 检测再探活 | 52.6s → 2.1s |
| LLM「JSON+后缀解释」贪婪正则解析失败 → 3 轮整调用重试 | `_extract_first_json` 括号平衡提取 | 每次诊断省约 2 分钟 |
| 进度频繁落库 | 0.8s 节流（终态直写） | DB 压力降一个量级 |

## 三、LangGraph 多智能体编排（创新点一）

### 3.1 图结构（`agents/graph.py`）
```
parser ∥ job_analyze → scorer → gap → clarify_plan →(有问→clarify_wait interrupt)→ rewriter → refine
```
- **并行节点**：parser/job_analyze 并行，LLM 耗时减半
- **条件边**：clarify_plan 产 0-3 问 → 动态走暂停或直通
- **refine 自省精修**：rewriter 产出后自审再修一轮（可关）

### 3.2 动态追问 = interrupt 人在回路（解决固定轮次）
1. `clarify_plan`：LLM 按信息缺口判「问不问」；**先提交 state 再 `interrupt()`**（恢复时零重复调用）
2. `clarify_wait`：`interrupt()` 暂停，问题经 SSE 推前端
3. 前端问题卡片 → `POST /live/clarify/{task_id}` → `Command(resume=answers)` 恢复
4. **MemorySaver checkpointer** 保管状态，任务终态 `delete_thread` 释放

### 3.3 关键工程决策（答辩高频）
- **Py3.10 async 图 interrupt 不可用**（contextvars 行为 3.11+ 才正确）→ 官方兼容解：同步节点包装 + worker 线程驱动同步 stream；离线图保持 async
- 结构化输出三层兜底（`agents/utils.py`）：代码围栏清理 → 括号平衡提取 → 纠错提示重试

## 四、RAG 证据接地（创新点二，最重点）

### 4.1 设计定位：任务内证据库（区别于传统外挂知识库）
- 传统 RAG：海量文档库检索知识答用户问题
- 本项目：把**当前简历+JD** 切块建临时索引，让每条诊断结论回链原文 → **可解释 + 抗幻觉**。不做海量库是场景判断（知识在输入内闭合），见 Q6

### 4.2 四步流水线（`core/evidence.py`）
1. **分块** `chunk_text()`：bullet 行独立成块（每条经历单独可引用）；200 字符目标长；稳定 id `R1/J1…`
2. **索引** `build_evidence_index()`：优先 OpenAI 协议 `/embeddings`；**降级** IDF 关键词检索（未配/429/超时 → 进程级熔断 `_EMBED_DISABLED`）
3. **检索** `retrieval_pool()`：多查询合并去重 Top-K；**M12 打分**：`Σ IDF(命中词) × √查询覆盖度 ÷ √块长度`（BM25-lite；IDF=`log(1+N/df)` 让「Kubernetes」比「负责」值钱；DF 表缓存 index 上）
4. **校验** `filter_valid_ids()`：LLM 引用逐一验真、去重；引用丢光 → `is_inferred=true`

### 4.3 三消费节点
| 节点 | 查询 | 注入 | 约束 |
|---|---|---|---|
| scorer | 六维度名+摘要 | 每维度 Top-3 | 评分带证据 |
| gap_agent | JD 原文块交叉检索 | 池 ≤10 条；**空池必须留空+推断，严禁编造 id** | 差距带 `evidence` 原文 |
| rewriter | 复用差距证据 | 忠于证据不得编造 | 建议带 evidence_ids |

### 4.4 防幻觉四层体系（答辩必背）
① 证据原文注入 prompt（grounding）② 只许引用池内 id（prompt 级）③ `filter_valid_ids` 输出校验（代码级）④ 无据标「推断」不删除（信息保留）

### 4.5 消融实验（数据详见技术说明文档第 13 章）
- **RAG 贡献 +8 分**（82 vs 74），引用率 100% vs 0%，推断率 ~0% vs 100%
- refine +1 分；稳定性 80.8±1.0
- **方法学漏洞发现**（加分素材）：首版消融 B 变体引用率 100% 假象 —— 空池下模型仍幻觉出恰好合法的 id，只禁检索不够，必须**检索+校验双禁**才是有效消融

## 十、答辩预设问题速答

**Q1 为什么不用向量数据库（FAISS/Milvus）？**
单任务 <100 块，纯 Python 余弦毫秒级；零依赖让打包 55MB 可控；`search_evidence` 接口化，要上向量库只换实现。

**Q2 embedding 不可用怎么办？**
三级降级：embeddings → 失败熔断 → IDF 关键词（BM25-lite）。消融证明关键词模式引用率已达 100%。

**Q3 怎么防止 LLM 编造？**
防幻觉四层（见 4.4）。消融 B 变体的幻觉 id 现象反证校验层必要性。

**Q4 为什么 LangGraph 而非裸调 API？**
需要条件分支、checkpointer 状态持久化、官方 interrupt/resume 原语、并行节点；裸 API 是线性流水线，自写要重造状态机且无断点恢复保证。

**Q5 追问为什么动态？**
固定轮次在信息充分时浪费用户时间、不足时问不透；LLM 按缺口判 0-3 问，「不为问而问」。

**Q6 为什么不做海量文档库 RAG？**
简历诊断知识在用户输入内闭合，外挂库零增量且有噪声；作为 future work 写入展望（岗位能力知识卡片混合检索，见技术说明 13.4）。
