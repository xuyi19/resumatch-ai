## 一、摘要与关键词素材（全文写完后回头打磨）

### 1.1 一句话定位（可改写）

> 面向校园招聘场景，设计并实现了一套**可解释、可交付**的简历—岗位诊断与优化系统。系统以 LangGraph 状态图组织多智能体诊断工作流，以任务内 RAG 证据接地保证每条结论可回链简历原文，通过动态追问补全信息后生成结构化优化简历，支持多模板 Word/PDF 导出，并以桌面免安装 exe 与匿名会话网站双形态交付。

### 1.2 三个创新点句式（对应第 4 章三小节）

1. **基于状态图的多智能体诊断工作流**：诊断任务拆解为职责单一的智能体，由 LangGraph 有向图编排；解析阶段并行化，追问阶段以 interrupt 原语实现「人在回路」的动态暂停—恢复，追问数量由模型按信息缺口判定（0~3 问），避免固定轮次的体验缺陷。
2. **任务内 RAG 证据接地方法**：区别于外挂知识库式 RAG，将当前简历与 JD 切块建立临时检索索引，使每条评分、差距与改写建议均可回链原文证据；通过「证据注入 → 引用约束 → 输出校验 → 推断标注」四层防幻觉体系，消融实验显示综合评分提升 8 分（82 vs 74），证据引用率 100%。
3. **面向异构大模型的结构化输出工程**：以「Schema 注入 → 括号平衡提取 → 纠错重试」三层容错兼容不稳定支持 Function Calling 的低价模型，并以字符状态机实现 JSON 字段级 token 流式增量解码，支撑面试对话的打字机体验与任意 OpenAI 协议模型的即插即用。

### 1.3 关键结果数字（摘要可用，详见 §10.1）

- 稳定性：3 用例重复评估综合分 80.8±1.0；消融：证据接地贡献 +8 分；SSE 单进程 150 并发首包 p95<0.5s；桌面启动提速 25 倍（52.6s→2.1s）；测试 188 pytest + 15 vitest。

### 1.4 关键词候选

简历诊断；大语言模型；多智能体；检索增强生成（RAG）；证据接地；LangGraph；结构化输出；流式推送（SSE）。

## 二、第 1 章 绪论素材

### 2.1 研究背景与痛点（可直接改写）

校园招聘与实习申请中，求职者面临两个典型痛点（源自技术说明 §1.1，可展开为「错配—海投—低反馈」的恶性循环）：

1. **人岗信息不对称**：难以判断「我适不适合这个岗位」，凭感觉海投，反馈率低；
2. **简历优化缺乏针对性**：市面工具只做通用性打分（格式/错别字/篇幅），无法结合**具体目标岗位**给出差异化改进方向，更不能直接给出可用的改写结果。

技术侧背景：大语言模型在文本理解与结构化抽取上已成熟，但单一 Prompt「一问一答」式点评输出发散、缺少中间过程、无法定位到简历具体段落——引出「需要工作流编排 + 证据接地」的系统设计动机。

### 2.2 国内外研究/产品现状对比表（绪论 1.2 节直接可用）

| 类别 | 代表 | 思路 | 局限（本文对比点） |
|---|---|---|---|
| 传统简历工具 | 各类模板站/评分工具 | 格式美化、通用性打分 | 无岗位针对性，不给改写结果 |
| 通用 LLM 直接问答 | ChatGPT 网页版等 | 单 Prompt 点评 | 输出发散、无中间过程、结论无证据可溯、幻觉风险 |
| 自动投递工具 | AIHawk（12k★） | 爬取+代投递 | 平台风控封号（Boss 2026 冻结约 2.5 万账号先例），核心已转商业闭源 |
| 岗位爬取脚本 | get_jobs（8.7k★） | 模拟请求抓取在招岗位 | 风控对抗无休止（作者自述智联模块失效），法律与封号风险由使用者承担 |
| 半自动投递助手 | Simplify Copilot（约 2M 用户） | 统一档案+表单预填+用户手点提交 | 只解决「投」环节，不解决「简历与岗位匹配」诊断 |
| **本系统** | 知岗 ResuMatch-AI | 多智能体诊断 + 任务内证据接地 + 动态追问 + 半自动投递辅助 | —（结论：证据可溯、过程可解释、交付可用、零封号风险） |

> 写法建议：表格后加一段「本文与上述工作的差异」：不爬取、不代投（产品红线，见 §九），把自动化收敛在「诊断与材料生成」这一 LLM 真正擅长的环节。

### 2.3 本文主要工作（绪论 1.3 节素材）

1. 设计并实现基于 LangGraph 的多智能体简历诊断工作流（解析并行化、条件分支、interrupt 动态追问、断点续跑）；
2. 提出并实现任务内 RAG 证据接地方法与四层防幻觉体系，完成消融实验证明其有效性（+8 分）；
3. 实现诊断进度与面试对话的 SSE 流式推送（进度逐节点推送；面试回应 token 级渐进渲染）；
4. 设计并实现数据驱动的求职过程归因能力：投递漏斗转化统计、匹配度分解矩阵（JD 逐条拆解 + 简历证据回贴校验）与简历版本赛马（分组转化对比），回答「卡在哪、哪版简历更有效」；
5. 构建稳定性/消融/压测三维评估体系，并以桌面 exe 与网站双形态交付（PyInstaller+pywebview 打包，单实例锁、免安装）。

### 2.4 论文组织结构（段落模板）

> 本文共分七章。第 1 章介绍研究背景与现状；第 2 章介绍系统涉及的关键技术；第 3 章给出系统需求分析与总体设计；第 4 章详述关键技术实现，包括多智能体工作流、证据接地方法与流式推送；第 5 章展示系统实现效果；第 6 章给出测试与实验评估；第 7 章总结全文并展望后续工作。

## 四、第 3 章 系统设计素材

### 4.1 需求分析

**功能性需求**（技术说明 §2.1 有完整清单，本文概括）：
- 简历接入：上传 PDF/DOCX/TXT、粘贴文本、编辑器直接创建；原件保留与原版式预览；
- 智能诊断：简历+JD → 六维评分 → 差距清单（带证据）→ STAR 改写建议；动态追问；失败断点续跑；
- 模拟面试：题目生成、多轮对话（token 级流式）、评分量化、总评与 Word 报告；
- 结果交付：14 模板 Word 导出（可嵌证件照）、PDF 导出、诊断报告导出；
- 求职管理（一句话带过）：岗位库/投递台账/刷题/Offer 比较/统计看板/数据备份。

**非功能性需求**（技术说明 §2.2）：免安装、零配置可用；数据本机隔离（owner_id 全表）；响应实时性（SSE）；输入安全（类型/大小/长度防线）；可插拔模型（任意 OpenAI 协议）。

### 4.2 总体架构（图素材）

分层文字图（画图时照此布局）：

```
前端 SPA（Vue3：诊断/报告/编辑器/面试/岗位库/工作台）
        │ REST + SSE（/api/v1/*）
后端 FastAPI（api/v1 路由与校验 → services 业务编排 → agents LLM 工作流 → core 配置/DB/检索）
        │
SQLite（aiosqlite+WAL：简历/诊断/面试/岗位/导出历史…）  文件目录（简历原件/证件照/导出产物）
        │
外部 LLM（OpenAI 协议：智谱/DeepSeek/通义…，用户自配 Key）
```

- **双形态**：`APP_MODE=local`（桌面 exe，owner 固定 local）/ `web`（HttpOnly 匿名 cookie `rmsid`，服务端 Key 每日配额 10 次）；同一套代码环境变量切换（技术说明 §1.4(3)）。
- **端到端请求链路**：技术说明 §4.3 有完整时序（画时序图照抄）。

### 4.3 诊断链图结构（LangGraph，画图素材）

```
parser ∥ job_analyze（并行）→ scorer → gap → clarify_plan
```

- refine 自省精修：rewriter 产出后自审再修一轮（可关）。

## 五、第 4 章 关键技术实现素材（重点章）

### 5.1 多智能体工作流与 interrupt 人在回路（对应创新点一）

1. **并行化**：parser 与 job_analyze 输入独立，从 START 并行出发（agents/graph.py）；
2. **动态追问**：clarify_plan 由 LLM 按信息缺口判定「问不问、问几个（0~3）」；先提交 state 再 `interrupt()`（恢复时零重复调用）；前端问题卡 → `POST /live/clarify/{task_id}` → `Command(resume=answers)` 恢复；MemorySaver/SqliteSaver 保管状态，任务终态释放；
3. **工程决策（答辩高频）**：Py3.10 异步图中 interrupt 的 contextvars 行为不正确（3.11+ 才修复）→ 采用官方兼容解：同步节点包装 + worker 线程驱动同步 stream；离线评估图保持 async；
4. **可靠性**：失败断点续跑（`/live/retry/{task_id}`，`ainvoke(None)` 从失败节点继续）；跨重启恢复（SqliteSaver + waiting 任务落库 + 启动补偿）。

### 5.2 任务内 RAG 证据接地与防幻觉四层（对应创新点二，全文最重点）

**设计定位**（务必写清，答辩必问）：传统 RAG 检索外挂知识库回答开放问题；本场景知识在「简历+JD」输入内闭合，因此把**当前输入**切块建临时索引，让每条结论回链原文——目标是**可解释与抗幻觉**，而非知识扩充。

**四步流水线**（core/evidence.py，画流程图素材）：
1. 分块 `chunk_text`：bullet 行独立成块（每条经历可单独引用），目标 200 字符，稳定 id `R1/J1…`；
2. 索引 `build_evidence_index`：优先 OpenAI 协议 `/embeddings`；失败/未配 → **进程级熔断**降级 IDF 关键词检索（BM25-lite：`Σ IDF(命中词) × √查询覆盖度 ÷ √块长度`）；
3. 检索 `retrieval_pool`：多查询合并去重 Top-K，按节点注入（scorer 每维度 Top-3；gap 池 ≤10；rewriter 复用差距证据）；
4. 校验 `filter_valid_ids`：LLM 引用逐一验真去重；引用丢光 → 标 `is_inferred=true`（信息保留而非删除）。

**防幻觉四层体系**（背下来）：
① 证据原文注入 Prompt（grounding）→ ② 只许引用池内 id（prompt 级约束）→ ③ 输出校验 filter_valid_ids（代码级）→ ④ 无据标「推断」不删除（信息保留）。

**消融实验数据**：见 §7.3（RAG 贡献 +8 分）。

### 5.3 结构化输出三层容错（agents/utils.py）

低价/开源模型常不稳定支持 Function Calling / JSON Mode。三层兜底：
1. Schema 注入：把 pydantic 模型的 JSON Schema 直接写进 Prompt（含字段说明 few-shot）；
2. 提取兜底：剥 Markdown 代码围栏 → `_extract_first_json` 括号平衡提取首个完整 JSON 对象（修复「JSON+后缀解释」贪婪正则失败问题，每次诊断省约 2 分钟）；
3. 纠错重试：解析失败把错误提示追加进 Prompt 重试（3 轮）。

**流式增量解码**（优化⑩亮点）：`_JsonFieldStream` 字符状态机从模型 JSON 输出中**边收边解码** `reply` 字符串值（支持转义/`\uXXXX`），实现面试回应 token 级打字机渲染；流结束后仍按完整文本严格解析 `advance`。三级降级：JSON 不合法但已流出发言 → 保留文本 advance 置 false；astream 中途抛错 → 回退非流式端点重试一次；会话校验失败 → 开流前正常 HTTP 4xx。

### 5.4 SSE 实时推送（两个场景）

- **诊断进度**：StreamingResponse + `text/event-stream`，逐节点推送进度/日志；断线 10 分钟内重连可续（内存任务表 TTL 1h），过期回退 DB 快照（含 owner 校验）；
- **面试对话流式**（优化⑩）：POST 无法用 EventSource（GET-only）→ 前端 fetch + ReadableStream 手工解析 SSE；后端 `astream` token 流式 + §5.3 增量解码；总评阶段发 `stage` 事件显示「正在生成总评…」。

### 5.5 双形态交付与轻量会话（对应创新点/亮点小节）

- 单代码库 `APP_MODE` 切换：local（owner 固定）/ web（HttpOnly cookie 匿名会话，30 天）；
- 不做用户系统即达多用户数据隔离（owner_id 全表）——答辩话术：**轻量会话设计**，隐私数据本机化，web 形态服务端 Key 限每日 10 次防滥用、自带 Key 不限。

### 5.8 求职归因与简历赛马（主线新能力，第 4/5 章新增小节素材）

> 定位：把「一次性诊断」升级为「数据驱动的持续归因」。数据底座 = 岗位库五态状态机（wish/applied/interviewing/offer/closed）+ 投递台账（apply_at 首投时间、apply_channel 渠道、apply_resume_id 关联简历）。全部纯本地计算（除匹配分解外零 LLM），体现「过程数据底座」价值。

**（1）投递漏斗与规则归因（M72，`GET /jobs/attribution`）**

- 口径（与周报/跟进提醒完全一致，论文可写成「统一口径设计」）：
  - 曾投过 = apply_at 落过时间 **或** 状态 ∈ {applied, interviewing, offer}（投后 closed 计入；wish 与从未投递的 closed 不计）；
  - 进面 = interviewing + offer；约面率 = 进面 / 曾投；Offer 率 = offer / 进面；
  - 停滞 = 当前仍 applied 且距 apply_at 超过 N 天（N 同跟进提醒设置，默认 7）。
- 规则归因产出「假设 + 建议动作」（每条附跳转目标路由），按严重度 high/medium/info 排序，上限 4 条。规则集覆盖：约面率偏低（简历与岗位错配 → 跳诊断）、Offer 率偏低（面试表达 → 跳模拟面试）、大面积停滞（跟进 → 跳岗位库）、投递量不足、投递渠道集中度提示。
- **诚实性设计（论文可提炼为「数据归因的诚实性原则」）**：投递样本 <5 份时不做转化归因、只输出「样本积累期」提示；closed 岗位是否面过无法回溯，明确不计数并在文案如实说明——与证据接地「宁降级不编造」一脉相承。

**（2）匹配度分解矩阵（M72.1，`POST /jobs/match-matrix`，简历诊断能力的横向延伸）**

- 单次 LLM 结构化调用把 JD 拆为 6~12 条要求：类别 ∈ {skill 硬技能, domain 领域业务, exp 经验年限, edu 学历, other 加分项}，权重 1~5（5=精通/必须/明确年限，3=熟悉/优先，1~2=加分），判定 ∈ {hit, partial, miss}，并要求 hit/partial 附简历原文逐字摘录（≤80 字）。
- **证据回贴校验（核心防幻觉算法，可与 §5.2 合并论述）**：对每条 evidence 做归一化（去所有空白 + 小写）后在简历全文做子串匹配——容忍换行/空格差异、不容忍改写；校验失败或 hit 无证据时该行强制降级为 partial、清空证据、gap 置「证据未能回溯到简历原文，请人工核对」。宁降级不编造。
- 加权评分：`score = round(Σ(wᵢ·vᵢ) / Σwᵢ × 100)`，v ∈ {hit=1.0, partial=0.5, miss=0.0}；另合并 M61 关键词覆盖结果（词库+jieba 双通道）作为词汇层互证。模型参数 temperature=0.1。
- 错误分流与全站一致：无 Key 400（引导设置页）/ LLM 异常 502。pytest 6 例覆盖真证据保留/编造证据降级/hit 无证据降级/无 Key/异常/参数校验。

**（3）简历版本赛马（D2，`GET /jobs/resume-race`）**

- 机制：岗位库标记「已投递」时关联所用简历（apply_resume_id，首次投递落库不覆盖，与 apply_at 同口径）；投递弹层复用 M61 体检的简历选择，零新增交互负担。
- 统计：按关联简历分组输出 投递数 / 进面数 / offer 数 / 约面率 / Offer 率（口径同漏斗），前端以条形对比呈现；回答「同一批岗位用 A/B 两版简历投，哪版约面率高」。
- 诚实性：未关联简历的投递与「简历已删除的历史关联」统一归「未记录」组如实展示（不编造标题）；每组投递数 <5 标注 sample_ok=false 并整体降透明度 + 文案「先积累样本，暂不下结论」。
- 实现要点：SavedJob 增列 apply_resume_id（轻量迁移 _SCHEMA_NEW_COLUMNS）；pytest 5 例覆盖分组口径/样本标注/删除兜底/不覆盖语义/owner 隔离。

**（4）论文写作建议**：三个能力可合成一章「基于过程数据的求职归因」，论证链 = 统一数据口径（状态机）→ 描述统计（漏斗）→ 归因规则（假设生成）→ 证据校验（防幻觉）→ 对照实验（赛马）；与第 4 章证据接地形成「结论可信 → 过程可归因」的完整叙事。

### 7.2 稳定性实验（数据源：技术说明 §13.1，glm-4-flash 免费档）

3 用例 × 2 次：后端岗高匹配 81.5±0.7 / 前端转后端低匹配 81.0±0.0 / 数据岗中匹配 80.0±1.4；
**汇总：总体均值 80.8，标准差 1.0**（<10 视为稳定），高/中/低匹配用例区分度合理。

### 7.3 消融实验（数据源：技术说明 §13.2，最硬核素材）

| 变体 | overall | 差距数 | 引用率 | 推断率 | 建议带据率 | 耗时(s) |
|---|---|---|---|---|---|---|
| A 完整（RAG+refine） | 82 | 3 | 100% | 0% | 100% | 134 |
| B 无 RAG 证据 | 74 | 6 | 0% | 100% | 100% | 142 |
| C 无 refine | 81 | 6 | 83% | 17% | 100% | 112 |
| D 在线+自动追问 | 78-82 | 3 | 100% | 0-33% | 100% | 140 |

结论：**RAG 证据接地贡献 +8 分**（82 vs 74），质的差异：引用率 100% vs 0%、推断率 ~0% vs 100%、差距条数 3 vs 6（无 RAG 时泛泛而谈条数虚增）；refine 贡献 +1 分。

**方法学漏洞发现（加分素材，体现实验素养）**：首版消融 B 变体引用率 100% 是假象——空池下模型仍幻觉出恰好合法的证据 id（如 R1），`filter_valid_ids` 对完整索引校验直接放行；用三个探针逐层定位后修正为「检索+校验双禁用」才构成有效消融。

### 7.4 压力测试（数据源：技术说明 §13.4，scripts/stress_web.py）

## 十一、答辩问答速答（扩充版）

**Q1 为什么不用向量数据库（FAISS/Milvus）？**
单任务 <100 块，纯 Python 余弦毫秒级；零依赖让打包 17MB 可控；`search_evidence` 接口化，要上向量库只换实现。

**Q2 embedding 不可用怎么办？**
三级降级：embeddings → 失败进程级熔断 → IDF 关键词（BM25-lite）。消融证明关键词模式引用率已达 100%。

**Q3 怎么防止 LLM 编造？**
防幻觉四层（§5.2）。消融 B 变体的幻觉 id 现象反证校验层必要性。

**Q4 为什么 LangGraph 而非裸调 API？**
需要条件分支、checkpointer 状态持久化、官方 interrupt/resume 原语、并行节点；裸 API 是线性流水线，自写要重造状态机且无断点恢复保证。

**Q5 追问为什么动态？**
固定轮次在信息充分时浪费用户时间、不足时问不透；LLM 按缺口判 0-3 问，「不为问而问」。先提交 state 再 interrupt，恢复零重复调用。

**Q6 为什么不做海量文档库 RAG？**
简历诊断知识在用户输入内闭合，外挂库零增量且有噪声；作为 future work 写入展望（行业考察点卡片混合检索）。

**Q7 Py3.10 下 interrupt 遇到过什么问题？**
异步图中 contextvars 行为 3.11+ 才正确；采用官方兼容解：同步节点包装 + worker 线程驱动同步 stream，离线图保持 async。

**Q8 面试对话怎么做到打字机效果？**
后端 astream token 流式 + 字符状态机从 JSON 增量解码 reply 字段（转义/\uXXXX 全支持）；前端 fetch+ReadableStream 手工解析 SSE（POST 不能用 EventSource）；三级降级保底。

**Q9 消融实验怎么保证有效？**
教训：只禁检索不够——空池下模型仍幻觉合法 id。必须「检索+校验双禁」。这个方法学漏洞本身就是答辩加分点。

**Q10 评分可信吗？**
稳定性 80.8±1.0（重复评估波动小）；高/中/低匹配用例区分度合理；正在补人工标注集 + LLM-as-judge 交叉验证（evaluate.py 基建就绪）。

**Q11 为什么不爬取岗位、不代投？**
平台无个人开放 API；代投封号实证（Boss 冻结 2.5 万账号）；爬取分发有法律风险。深链跳官方页是合规桥接，自动化收敛在诊断与材料生成。

**Q12 网站形态没有用户系统，数据怎么隔离？**
HttpOnly 匿名 cookie（30 天）+ 所有业务表 owner_id 隔离；桌面形态固定 local。轻量会话设计，够用且零注册摩擦。

**Q13 为什么 SQLite 而不是 MySQL？**
免安装单文件是「零配置交付」的前提；WAL 模式实测 ~400 ops/s 写吞吐，远超单用户业务流量 3 个数量级。

**Q14 系统安全做了什么？**
输入魔数白名单/长度截断、JD 注入防护（embed_jd_text + 6 注入点）、重复诊断 409、Key 不入库不入包、扫描件明确引导。

**Q15 性能上最得意的一条优化？**
启动 52.6s→2.1s：根因是端口探测串行健康检查；先 `SO_EXCLUSIVEADDRUSE` 独占 bind 探测再探活。（`SO_REUSEADDR` 在 Windows 会误判，踩坑记录在案。）
