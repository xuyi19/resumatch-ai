## M8 启动性能 + 双形态界面 + 首页重写（2026-09-18）

- [x] **exe 启动提速 25 倍（52.6s → 2.1s）**：根因是 `_find_running_port()` 对 8765+50 区间逐个发 HTTP 健康检查，而本机对「已关闭端口」做 TCP 连接不会立刻拒绝、会静默挂满 1 秒超时 → 全空闲时白等 50.85 秒。改为先用 bind 探测（纯本地、瞬时）跳过空闲端口，只有被真正占用的端口才 connect 验证身份；`_wait_ready` 同样先判端口再探活。实测冷启动 2.09s / 热启动 1.94s / 窗口出现 2.86s
- [x] **运行形态下发**：新增 `GET /api/v1/meta`（app_mode / version / build_tag / daily_limit / has_server_key），前端据此切换界面，避免维护两套代码

## 环境与约定（备忘）

- 后端 conda 环境（真实路径）：`E:\conda\envs\resumatch-ai\python.exe`（`C:\Users\许\.conda\envs\resumatch-ai` 是 junction，可能被清理工具删除）；测试：`cd backend && python -m pytest tests/`
- 环境若被清理工具破坏：`Lib/` 标准库与 `DLLs/` 可用 python.org 嵌入包（3.10.11）补齐，`site-packages` 通常完好；`pip` 用 get-pip.py 的 `--target` 方式绕过 `Scripts\*.exe` 被杀软拦截的问题
- 测试隔离：conftest 在导入 app 前把 `DB_URL` / `PHOTOS_DIR` 指向 `backend/tests/.tmp/`（自检断言，隔离失效即报错），并手动 create_all + ensure_schema_columns（ASGITransport 不触发 lifespan）；测试不再写入开发库 `backend/data/resumatch.db`
- 老库升级模式：新增列统一登记在 `app/core/db.py` 的 `_SCHEMA_NEW_COLUMNS`
- 本机 8765 端口常被「蓝笔申论 BluePencil」占用，ResuMatch 会顺延 8766+
- 前端路由为 hash 模式（`#/analyze`），自动化导航必须带 `#`
- SQLite 时间戳为 UTC naive；配额/启动补偿的日期比较均按 UTC
