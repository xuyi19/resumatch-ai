# ResuMatch AI 项目分析报告

> 分析日期：2026-09-11 · 代码基线：`c26d913` · 后端 2742 行 Python / 前端 958 行 Vue

---

## 一、一句话定位

上传简历 → 实时爬取智联岗位 → 混合打分排序 → 5 个 LLM Agent 串行诊断 → 输出六维评分 + 差距分析 + 改写建议 + 优化后简历（可导出 Word）。

技术栈：FastAPI + SQLAlchemy 2.0 async + MySQL + LangGraph + DeepSeek + sentence-transformers + Playwright + Vue3/Vite/Tailwind。

---

## 二、架构链路

```
[前端 Vue3]
   │ 1. POST /resumes/upload（PDF/DOCX → 文本）
   │ 2. POST /live/analyze {resume_id, keyword, city}
   ▼
[FastAPI] ── asyncio.create_task ──▶ [LivePipelineService 后台任务]
                                        │
   ┌────────────────────────────────────┼────────────────────────────┐
   │ ① Playwright 爬智联（sync 版，2 页）                              │
   │ ② JobPipeline 去重入库（source_id 唯一）                          │
   │ ③ MatchService.rank_jobs（全表扫描 + 打分）                        │
   │      score = 0.4×技能 + 0.3×语义 + 0.2×经验 + 0.1×学历              │
   │ ④ DiagnosisService → LangGraph 串行 5 节点                        │
   │      parser → scorer → gap → rewriter → optimizer                 │
   │ ⑤ 落库 diagnosis_records，删除本次爬取岗位                          │
   └──────────────────────────────────────────────────────────────────┘
   │
   ▼ 前端 2 秒轮询 /live/status/{task_id} 拿进度与结果
```

状态持久化是双轨的：内存 `TASKS` 字典供轮询，MySQL `diagnosis_records` 供历史页。服务重启后轮询 404，前端会回落到历史接口兜底——这个兜底设计是对的。

## 三、做得好的地方（答辩能讲的）

| 项 | 说明 |
|---|---|
| **文档质量罕见地扎实** | `docs/问题解决记录.md` 16KB，7 大类 20+ 个真实踩坑（MySQL 特殊字符密码、Playwright 与 uvicorn 事件循环冲突、DeepSeek 不返回 JSON…）。这份文档本身就是毕设加分项，也是面试时能聊出深度的素材。 |
| **异步全链路** | asyncmy + AsyncSession + 连接池参数（pool_pre_ping / pool_recycle）配置到位，不是照抄模板。 |
| **防御性细节** | LLM JSON 解析带 3 次重试且逐次追加纠错提示；Pydantic `field_validator` 兜住 `overall` 收到对象的畸形输出；爬虫翻页做了重复页检测。 |
| **数据不留存** | 任务结束主动删除爬取岗位，规避数据合规风险，这个意识比多数课设强。 |
| **UI 完成度高** | 拟物化风格统一，雷达图 + 进度条 + 历史页齐全，不是"能跑就行"的水平。 |

## 四、问题清单（按修复优先级）

### P0 — 不修会影响验收 / 演示

**1. `requirements.txt` 严重残缺**
缺失：langgraph、langchain-openai、sentence-transformers、torch、playwright、sse-starlette、pymupdf、python-docx、tenacity、numpy。当前文件只有 44 行，且版本像是另一个环境的 `pip freeze`。

后果：任何人（包括答辩老师、面试官）clone 后 `pip install -r requirements.txt` **必然跑不起来**。这是作品集最致命的一类问题。

修复：在真实 venv 里重新 `pip freeze > requirements.txt`，或手写按功能分组的依赖清单（推荐，更专业）。**0.5 小时**。

**2. `asyncio.create_task` 未持有引用（真 Bug）**
`app/api/v1/live.py:40`：
```python
asyncio.create_task(LivePipelineService.run(...))   # 返回值被丢弃
```
asyncio 只持有 task 的弱引用，GC 时该任务可能被静默回收，表现为"偶尔任务卡在 pending 不动"。

修复：模块级 `BACKGROUND_TASKS: set[asyncio.Task]()`，创建后 add，task 完成时 `discard`。**10 分钟**。

**3. 无量化评估，算法无法自证**
目前"匹配准不准"全靠肉眼。毕设答辩第一问就是"你怎么证明你的排序算法有效"。

修复：手工标注 50~100 条 `(简历, 岗位, 相关度 0-3)`，算 Precision@10 / NDCG@10，做消融实验（纯关键词 / 纯语义 / 当前加权 / 加权+重排），出一张对比表。**1.5~2 天，性价比最高的一项**。

---

### P1 — 影响专业评价

**4. "多智能体"含金量不足**
LangGraph 图是纯串行 5 节点：无分支、无循环、无并行、无 checkpoint、无 human-in-the-loop。本质是 Prompt Chain，用 for 循环也能写。

答辩必被问："为什么要用 LangGraph？"

低成本加分改造（选做 2 项即可，约 1 天）：
- **加 self-refine 循环**：`optimizer` 后接评分校验节点，overall < 阈值则回炉 `rewriter`，设最大迭代 3 次 → 这就是真正的 agentic 行为
- **加 checkpoint**（`MemorySaver` + `thread_id`）：支持中断续跑、过程可回放
- **加并行分支**：`scorer` 后并行跑 `gap`（人岗差距）与 `jd_keyword_extract`（JD 关键词抽取），再汇合到 `rewriter`

**5. 语义匹配性能与区分度双低**
- `rank_jobs` 每个岗位单独 `model.encode([resume, job])`，N 条岗位 = N 次推理。应改为一次性 encode 全部岗位再批量算 cosine。**改完速度提升一个量级，还能写成"性能优化"章节。**
- `semantic_similarity` 用 `(sim+1)/2` 映射。长文本余弦相似度普遍落在 0.3~0.7，映射后全挤在 65~85 分，等于这项权重 30% 的分数几乎没有区分度。建议做分位数校准，或换 `bge-reranker-base` 做二阶段重排。

**6. 技能匹配误报**
`extract_skills` 用子串包含：`"go" in text_lower`。`django` 会命中 `go`，`javascript` 命中 `java`，`mysql` 命中 `sql`。

修复：正则词边界 + 别名表（`golang→go`、`js→javascript`）。**0.5 小时**。

**7. 数据结构污染**
`gap_agent` 把总结塞进列表：`gaps.append({"summary": ...})`；`rewriter` 同理塞 `overall_advice`。前端必须 `.filter(g => !g.summary)` 过滤。类型已经劣化成 `list[dict | str]`，加字段就崩。

修复：改成 `{"items": [...], "summary": "..."}`，前后端同步改。**30 分钟**。

**8. 死代码 / 重复代码**
- `app/agents/nodes/docx_generator.py`（65 行）与 `app/utils/docx_generator.py`（235 行）重复，前者未被引用 → 删
- `app/crawlers/zhilian.py`（152 行 async 版）未被引用，实际用 `zhilian_sync.py`（文档 3.5 记录过 Windows 事件循环冲突才改用 sync）→ 删，或加注释说明保留原因
- `CrawlTask` 实体定义了建表但全项目零引用 → 删或实现
- `app/api/v1/match.py` 的 `/recommend`、`/with-diagnosis` 与 `PipelineService` 前端完全没用到

**9. 无认证、无 CORS**
- 全接口裸奔，`DELETE /history/{task_id}` 任何人可调用
- `main.py` 无 CORS 中间件，现在靠 Vite proxy 绕过，独立部署必跨域
- `vite.config.js` 开了 `host: 0.0.0.0` + `allowedHosts: true`，开发机在局域网内裸奔

**10. 前端传 LLM API Key**
`llm_config` 从请求体传明文 key。演示方便，但生产不安全，且 key 会进日志。建议改为服务端配置，或 session 级加密存储。

### P2 — 锦上添花

- 无 Alembic 迁移，靠 `create_all` 建表
- 全局 `TASKS` 字典导致无法多 worker 部署（目前靠单进程 + DB 兜底，可接受）
- 任务无取消机制，用户关页面后台还在跑
- 测试仅 4 个文件、覆盖纯函数，Agent 层无 mock 测试
- 无 token 消耗统计与限流
- 串行 5 次 LLM 调用导致端到端 3~5 分钟，是体验瓶颈

## 五、面试/答辩预设问题

| 问题 | 现状 | 建议答法 |
|---|---|---|
| 为什么用 LangGraph 而不是串行调用？ | 当前确实只是串行 | 改造后答：checkpoint 支持中断续跑、self-refine 循环、并行分支；改造前如实说是 Prompt Chain，规划了 X |
| 匹配权重 0.4/0.3/0.2/0.1 怎么定的？ | 硬编码，无依据 | 必须补消融实验，否则这题无解 |
| 怎么证明比关键词匹配好？ | 无评估 | 标注集 + NDCG@10 对比表 |
| 简历数据怎么处理隐私？ | 存 MySQL 未脱敏 | 提加密存储 + 自动清理策略，说"意识到了，规划中" |
| 爬取智联的法律风险？ | 无说明 | 强调仅用于个人研究、低频低量、用完即删（现有 delete 逻辑可以讲） |
| 端到端 3-5 分钟怎么优化？ | 未优化 | 批量 encode + 节点并行 + 流式输出，能讲出具体数字最好 |

## 六、修复路线建议

**第一轮（半天，必做）**：requirements.txt 补全 → create_task 强引用 → 技能词边界修复 → 删死代码

**第二轮（2 天，提含金量）**：标注集 + 消融实验（最高优先级）→ 语义批量 encode 优化 → LangGraph 加 self-refine 循环 + checkpoint

**第三轮（按需）**：CORS + 简单鉴权 → Alembic → Agent mock 测试 → 任务取消

如果时间只够做一件事，做**标注集 + 消融实验**。它能同时解决答辩、面试、论文三个场景里最致命的"你怎么证明有效"。
